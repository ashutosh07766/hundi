# WHAT BROKE

Running log of every real breakage and its fix. Newest first.

## 2026-09-03 — Refund threw a 500 *after* the money moved: a CHECK constraint the schema had but the live DB didn't
Adding human-issued refunds meant writing a `refund_issued` row to the hash-chained ledger. The event type was added to `schema.sql`'s `ledger_events.event_type` CHECK, every test passed against a fresh in-memory DB, and it shipped. The first refund against the real, long-lived `hundi.db` returned a bare `INTERNAL_ERROR` — *after* Razorpay had already issued the refund. `CREATE TABLE IF NOT EXISTS` never rewrites an existing table's constraints, and SQLite has no `ALTER … ALTER CONSTRAINT`, so the on-disk table still carried the old CHECK and rejected `refund_issued` on insert. The additive `ALTER TABLE ADD COLUMN` migration path covers new columns but not constraint changes. Result: a real reversal orphaned with no ledger record, and the retry double-called the provider (caught only because Razorpay itself rejects a duplicate).

Fix: `healLedgerEventTypeCheck` (`db/index.ts`) runs at open — when the live CHECK is missing a value the current schema allows, it rebuilds the table (rename aside → recreate from schema → copy every row verbatim, `seq`/`prev_hash`/`row_hash` preserved so the hash chain still validates → drop the old), with the append-only triggers dropped first so the schema re-binds them to the rebuilt table. No-op once healed, additive-only. The refund route now also maps a provider failure to a clean `502 REFUND_PROVIDER_ERROR` with Razorpay's own reason instead of a 500, and never writes the ledger row when the provider call fails. Proven with a real test-mode refund (`rfnd_...`) that is idempotent on replay and appends `refund_issued`. Lesson: "tests are green" against a fresh DB says nothing about a schema change that only an *existing* DB can reject — migrations for constraints are their own discipline.

## 2026-09-03 — Purpose-locking almost re-opened the exact hole it was meant to close
The first cut of purpose-locked mandates matched a signed keyword set against each product's title/brand/description to decide whether a cart was on-goal. That is a self-inflicted vulnerability: the text being matched is *merchant-controlled*, i.e. authored by the party the gate is supposed to constrain. A merchant could stuff "pairs with your running shoes" into a blender's description and a shoes-only mandate would pass it. The invariant it violated: **the classification the gate reads must not be controllable by the gated party.**

Fix: purpose-locking is now pure set-membership between two *signed* sets — the human's `allowed_skus` and the agent's cart SKUs (each cart SKU is separately price-checked against the live catalog). No free-text matching anywhere; the merchant can't widen the authorized set by editing copy, and the agent can't buy a SKU that isn't on the human's list. A rejection returns the allowed set so the failure is legible. Proven live: a mandate pinned to the sneaker SKU accepts the sneaker and rejects the socks with `GOAL_MISMATCH`. Lesson: an allow-list is only as trustworthy as the thing it keys on — key it on a value neither the merchant nor the agent can forge, never on text one of them writes.

## 2026-08-24 — Mandate was single-use but named like a wallet, so the agent stated a false balance
A real buyer session surfaced the worst kind of bug: the agent told the user "₹501 left" four times. It computed that from ₹5,000 − ₹4,499 because the field is `ceiling_paise` and a ceiling reads as a cumulative cap — but the mandate was single-use: one capture flipped the allowance to `consumed`, evaporating the rest. Nothing in the API reported consumed/remaining state, so the agent had no way to know it was wrong until the next purchase bounced `ALLOWANCE_CONSUMED`. A confident false balance is a trust failure, not just a bug, and single-use also breaks "give yourself ₹5,000 and buy me socks and a wedge cushion" — the second purchase can never land.

Fix: made the ceiling a cumulative wallet. Captures no longer consume the allowance (`reconcile.ts`); the verify gate measures `already-captured spend + this cart` against the ceiling (`verify-logic.ts` computes the captured sum, `core/verify.ts` enforces it); `one_live_settlement_per_mandate` still serializes in-flight spends so the cumulative cap can't be raced. The facilitator now exposes `spent_paise`/`remaining_paise`/`state (active|consumed|expired|revoked)` on `/mandates`, and `get_agent_identity` surfaces them — so the agent reads the balance instead of computing one (which lets the "never compute a balance" prompt crutch be deleted). Proven live: two ₹4,499 pairs captured under one ₹12,000 mandate (₹12,000 → ₹7,501 → ₹3,002), the third rejected AMOUNT_EXCEEDS_CEILING with the mandate still active.

Reordering catch: the wallet exposed that `AMOUNT_EXCEEDS_CEILING` was checked BEFORE `MANDATE_REVOKED`. Under single-use each cart was measured in isolation, so a valid post-revoke cart passed the budget check and reached the revocation check; under the wallet, cumulative spend tripped the budget check first, so a revoked mandate wrongly reported a budget error. Fixed by checking mandate liveness (expired/revoked) and scope before budget arithmetic — a dead mandate must say it's dead, not "over budget."

## 2026-08-24 — Variant purchases all failed SIG_INVALID_CART — the ingest schema silently stripped variant_id
Real Claude Desktop hit it first: every attempt to buy a specific size resolved the variant correctly, then died at cart-signature verification with `SIG_INVALID_CART` (the agent stopped after three tries and confirmed nothing was charged — the guard held). Non-variant purchases had always worked, so the discriminator was the variant itself. A standalone repro (`agents/scripted-brain/bin/prove-variant-purchase.ts`) reproduced it against the live facilitator using the same modules the MCP tool uses — ruling out a stale Claude Desktop process and proving a real bug.

Root cause: the variant build added `variant_id` to the signed cart (`cartSigningBytes` in core), the MCP/brain signers, verify.ts's manual validation, and the DB — but not to the facilitator's **Zod ingest schema** (`cartItemSchema` in `schemas.ts`). Zod strips unknown keys by default, so `variant_id` was dropped at the door of POST /settlements; the facilitator then recomputed the signing bytes from a cart the agent never signed (no variant_id) and the signature failed. The signature check was doing its job — the cart it verified genuinely wasn't the one that was signed.

Fix: added `variant_id`/`variant_label` as optional fields to `cartItemSchema` so they survive ingest, and widened core's `CartItem` optionals to `string | undefined` so the Zod-inferred type feeds the signed type cleanly under `exactOptionalPropertyTypes`. Proven with `pay_TTLfMqxA7OI65G` — a real test-mode capture of the 11UK sneaker with the variant bound in the signed cart and recorded in the ledger. Regression test in `http-settlements.test.ts` posts a signed variant cart and asserts it is not rejected SIG_INVALID_CART and that the stored cart retains the variant. Lesson: when a field becomes part of a signature, every hop between signer and verifier must preserve it byte-for-byte — a validation layer that helpfully drops "unknown" keys is a signature-breaker.

## 2026-08-24 — Variants: the "size reaches the merchant" claim was built on a false premise
The variants feature captures the size/color the human authorized and binds it into the agent's signed cart + the hash-chained ledger — that part is real and kept. But the build also wired the chosen variant into the settlement path so the checkout driver would navigate to the merchant's real Shopify cart permalink (`{storeOrigin}/cart/{variantId}:{qty}`), on the assumption the driver drives the merchant's own checkout. It does not. The driver only ever embeds Razorpay's TEST-mode `checkout.js` overlay on this process's own local host page; no code anywhere creates a real merchant order. So the variant-navigation branch would (1) never render the Razorpay overlay it waits for on a real Shopify checkout → every variant purchase times out and fails settlement, and (2) if pointed at a live store that *does* embed Razorpay, drive a real, live-mode payment — violating the project's absolute TEST-MODE-ONLY invariant.

The build agent flagged the mismatch instead of presenting it as done — which is exactly why it was caught before it shipped. Fix: removed the variant→storefront navigation from the settlement path entirely (`resolveVariantTarget` and the `variant` arg threading in `executor.ts`; `VariantCartTarget`, `buildVariantCartUrl`, and the navigation branch in `rails/checkout-driver.ts`, plus their tests). The driver is now unconditionally local-host-only, with a comment stating the invariant so a future edit doesn't re-introduce the landmine. What survives is the honest, valuable part: the authorized variant is signed and recorded, so Hundi's output carries the exact size — and handing that to a merchant's real order API is the production integration point, which must never run through the test-mode payment robot. Lesson: an assumption about *someone else's* runtime (here, "our driver drives the merchant's checkout") is as dangerous as one about the payment rail — verify the actual call path before building on it.

## 2026-08-23 — Adversarial self-review found the single-key collapse (agent could self-approve)
The product's central claim is that an autonomous agent structurally *cannot* approve its own above-threshold payment — only the human signer can. An adversarial re-read of `packages/core/src/verify.ts` found the claim was false: a rule (`AGENT_KEY_MISMATCH`) forced the mandate's registered credential to equal `intent.agent_pubkey_hex`, and the intent signature, the cart signature, **and** approvals all verified against that one key. Three roles collapsed onto one keypair — so the agent's own key was also the approval key, and the agent could approve its own settlement. The human-in-the-loop gate was cosmetic.

Fixed with real two-key separation. The registered credential is now the **human** key (signs the intent, approvals, revocations); the **agent** key is `agent_pubkey_hex`, embedded in the human-signed intent (so the human attests it) and used only to sign carts and decision narration. `verify.ts` dropped the `AGENT_KEY_MISMATCH` equality rule entirely and now verifies the cart against `intent.agent_pubkey_hex`, not the registered credential. The facilitator's approval/revoke routes already verified against the registered credential, so once registration stored the human key they required the human key with no route change. New adversarial tests encode the fix: the agent key can no longer produce a valid approval or revoke (fail-closed, settlement stays `pending_approval`), and the previously-impossible two-key happy path (intent signed by a distinct human key, cart by the agent key) now verifies. This is the "what broke and how we caught it" story: the RFC described the two-party model correctly all along; the code didn't do it until an adversarial review compared the two.

## 2026-08-23 — Day 1 spike: two assumptions died in contact with reality
1. The S2S JSON create-payment endpoint (the one Razorpay's own MCP server wraps) returned "URL not found" on a fresh test account — it's enablement-gated. Re-architected same hour to the embedded-checkout Playwright driver per the pre-agreed decision rule.
2. Razorpay docs say Orders `receipt` is enforced-unique. It is not — two identical-receipt orders were accepted. Our facilitator's own idempotency store is now the sole dedup guard on order creation. The trust envelope has to bring its own guarantees; the rail provides fewer than documented.
