# Hundi vs. the agent-payments protocol landscape

## Why now

Three separate efforts landed within twelve months of each other, all solving
the same problem from a different angle: an AI agent that can browse a
catalog and call a checkout API can also be tricked, over-reach, or simply
get bugged into spending money it was never authorized to spend. Google's
AP2, OpenAI/Stripe's ACP, and NPCI's emerging Unified Agent Protocol (UAP)
each answer "how does a human grant a bounded, verifiable spending authority
to software, and how does a merchant or rail trust that authority without
trusting the agent itself." None of them are settled standards yet -- AP2 and
ACP are both roughly a year old, and UAP is not yet public. The liability
question underneath all three is the same: when an agent buys the wrong
thing, or too much, who is on the hook, and what evidence exists to decide.
Hundi is a working implementation of that same trust-envelope shape, built
end to end over Razorpay/UPI-fiat rails, with a deterministic verification
gate that is the only thing standing between an agent's judgment and a
merchant's money.

## The three protocols, briefly

- **AP2 (Agent Payments Protocol)** -- Google, announced September 2025 with
  60+ launch partners (Mastercard, Amex, PayPal, Coinbase, Salesforce, and
  others). Defines a chain of W3C Verifiable Credentials -- an Intent
  Mandate, a Cart Mandate, and a Payment Mandate -- each cryptographically
  signed. The Cart Mandate is generated by the *merchant* (it embeds a
  `merchant_authorization` field attesting price and line items) and then
  signed by the *user's* device key to approve it -- a nested, two-party
  signature on the same object. Open protocol, reference implementations on
  GitHub. [Google Cloud: Announcing AP2](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol)
- **ACP (Agentic Commerce Protocol)** -- OpenAI, Stripe, and Meta, released
  under Apache 2.0 in September 2025. Payment moves through a **Shared
  Payment Token (SPT)**: single-use, time-bound, and scoped to one merchant,
  one currency, and one maximum amount. The merchant references the token
  inside a normal Stripe PaymentIntent; if the merchant tries to charge a
  different amount, Stripe rejects it. There is no cart-signing step and no
  durable budget -- the token is consumed by the one purchase it was minted
  for. [Stripe docs: shared payment tokens](https://docs.stripe.com/agentic-commerce/concepts/shared-payment-tokens),
  [Stripe docs: ACP](https://docs.stripe.com/agentic-commerce/acp)
- **UAP (Unified Agent Protocol)** -- NPCI's proposed standard for agent-led
  UPI payments, built on the existing **UPI Circle** delegated-payment
  mechanism: a user grants a secondary party (here, an AI agent) a spending
  limit plus consent controls, without changing UPI's underlying rails. As
  of this writing UAP is not yet public and is reportedly pending RBI
  approval; NPCI is widely expected to unveil it at Global Fintech Fest
  Mumbai (Sept 9-11, 2026). Razorpay and NPCI have already piloted a related,
  live agentic-UPI flow with Zomato/Swiggy/Zepto on Claude (Feb 2026). We
  could not find a published UAP spec to verify field-level detail against
  -- everything below is sourced from reporting, not a primary spec, and is
  flagged as such. [Inc42: NPCI to launch agentic payments on UPI](https://inc42.com/buzz/npci-to-launch-agentic-payments-on-upi-report/),
  [Stellagent: NPCI Unified Agent Protocol](https://stellagent.ai/insights/india-npci-unified-agent-protocol-upi)

## Concept mapping

| Concept | AP2 | ACP | UAP (reported, unverified) | Hundi today |
|---|---|---|---|---|
| Authorization credential | Intent Mandate -> Cart Mandate -> Payment Mandate, chained Verifiable Credentials | Shared Payment Token (SPT) | UPI Circle delegation: consent + spending limit | Ed25519-signed `IntentMandate` (`ceiling_paise`, `approval_threshold_paise`, `merchants[]`, `expires_at`, `goal` as advisory text) hash-chained to an agent-signed `CartMandate` |
| Who attests cart contents/price | the merchant (embedded `merchant_authorization`), countersigned by the user | n/a -- no cart signature; Stripe rejects amount tampering at charge time | not public | the **agent** signs the cart; the facilitator cross-checks each line item against its own CLI-scanned catalog-price registry (`PRICE_MISMATCH`) instead of a merchant signature |
| Spending scope | Cart/Payment Mandate = one purchase; an Intent Mandate can carry rules for a delegated/recurring task | strictly single-use -- one merchant, one amount, one expiry, then dead | a spending limit set at delegation time, usable across multiple transactions (rail-enforced) | a **cumulative wallet**: `ceiling_paise` caps total captured spend across many purchases, not one -- closer in shape to UAP's durable limit than to ACP's single-use token |
| Per-merchant / per-line granularity | merchant is fixed per cart | merchant is fixed per token | not public | signed `merchants[]` allowlist plus optional `per_merchant_ceiling_paise` sub-caps on top of the global ceiling |
| Human-in-the-loop gate | user signs the Cart/Payment Mandate directly, or pre-sets rules in the Intent Mandate | user approves SPT issuance up front; no further per-purchase step within scope | consent + limit set at delegation time | `needsApproval` fires above `approval_threshold_paise` **or** when cumulative spend would cross `cumulative_approval_threshold_paise`; approval is a `{settlement_id, mandate_cart_hash, decision}` object signed by a key the agent structurally never holds |
| Rail | protocol-level, rail-agnostic (cards, bank transfer, stablecoins via an x402 extension) | Stripe-processed, any ACP-compliant PSP | UPI, live | Razorpay **test mode**, embedded-checkout browser automation (netbanking only completes hands-free) |

Where Hundi is honestly a hybrid: its ceiling is a durable-budget primitive
like UAP's delegated limit, not a single-use token like ACP's SPT -- and its
per-cart line-item verification is closer to AP2's Cart Mandate in spirit,
but agent-signed against a scanned price registry rather than
merchant-signed. It borrows AP2's two-mandate hash-chain shape and
implements it without requiring a merchant to hold a signing key at all.

## What Hundi adds beyond the specs today

- **A hash-chained, append-only ledger.** Every state-changing event
  (`mandate_registered`, `verify_rejected`, `payment_captured`, ...) writes a
  row whose hash covers the previous row's hash, in the same DB transaction
  as the business write it records. `verify-ledger` walks and recomputes the
  whole chain independently. None of the three protocols above publish an
  equivalent tamper-evident audit log as part of the spec itself -- it is
  left to the implementer.
- **Structural two-key separation, not a policy convention.** The human's
  registered credential signs the intent, approvals, and revocations; the
  agent holds a distinct key, embedded in the human-signed intent, that can
  sign carts and nothing else. This was caught and fixed by an adversarial
  review that found a single-keypair collapse in an earlier build (see
  `WHAT-BROKE.md`, 2026-08-23) -- there is now a test proving the agent's key
  cannot produce a valid approval or revocation.
- **A fixed-order, fully enumerated rejection matrix.** `verify.ts` runs a
  deterministic sequence of checks and returns the first failure --
  `SIG_INVALID_INTENT` before `PRICE_MISMATCH` before `AMOUNT_EXCEEDS_CEILING`,
  every time, for the same input. Combined with a cumulative
  `cumulative_approval_threshold_paise`, this also closes a cart-splitting
  gap a per-cart threshold alone leaves open (many sub-threshold carts
  quietly draining a ceiling).
- **Merchant onboarding with zero signing-key integration.** A CLI (`npx
  hundi init`) scans any schema.org-marked-up storefront into a price
  registry the facilitator cross-checks against. This trades AP2's
  contemporaneous merchant signature for something that works on *any*
  existing store today, at the cost of trusting whatever price was last
  scanned -- a real, disclosed tradeoff, not a hidden one.

## Not yet / out of scope

Settlement runs entirely against **Razorpay test mode** via a Playwright
browser driving the embedded checkout overlay -- there is no integration
with a merchant's real order-creation API anywhere in the stack. Only
netbanking (via Razorpay's own mock-bank popup) completes hands-free; card
automation is blocked by bot-detection/fraud tooling, and UPI was not
offered on the test account used. The size/variant a human authorizes is
signed and recorded in the mandate chain, but handing that off to a real
merchant order is explicitly the next integration point, not something this
build does today.
