# WHAT BROKE

Running log of every real breakage and its fix. Newest first.

## 2026-08-24 — Variants: the "size reaches the merchant" claim was built on a false premise
The variants feature captures the size/color the human authorized and binds it into the agent's signed cart + the hash-chained ledger — that part is real and kept. But the build also wired the chosen variant into the settlement path so the checkout driver would navigate to the merchant's real Shopify cart permalink (`{storeOrigin}/cart/{variantId}:{qty}`), on the assumption the driver drives the merchant's own checkout. It does not. The driver only ever embeds Razorpay's TEST-mode `checkout.js` overlay on this process's own local host page; no code anywhere creates a real merchant order. So the variant-navigation branch would (1) never render the Razorpay overlay it waits for on a real Shopify checkout → every variant purchase times out and fails settlement, and (2) if pointed at a live store that *does* embed Razorpay, drive a real, live-mode payment — violating the project's absolute TEST-MODE-ONLY invariant.

The build agent flagged the mismatch instead of presenting it as done — which is exactly why it was caught before it shipped. Fix: removed the variant→storefront navigation from the settlement path entirely (`resolveVariantTarget` and the `variant` arg threading in `executor.ts`; `VariantCartTarget`, `buildVariantCartUrl`, and the navigation branch in `rails/checkout-driver.ts`, plus their tests). The driver is now unconditionally local-host-only, with a comment stating the invariant so a future edit doesn't re-introduce the landmine. What survives is the honest, valuable part: the authorized variant is signed and recorded, so Hundi's output carries the exact size — and handing that to a merchant's real order API is the production integration point, which must never run through the test-mode payment robot. Lesson: an assumption about *someone else's* runtime (here, "our driver drives the merchant's checkout") is as dangerous as one about the payment rail — verify the actual call path before building on it.

## 2026-08-23 — Adversarial self-review found the single-key collapse (agent could self-approve)
The product's central claim is that an autonomous agent structurally *cannot* approve its own above-threshold payment — only the human signer can. An adversarial re-read of `packages/core/src/verify.ts` found the claim was false: a rule (`AGENT_KEY_MISMATCH`) forced the mandate's registered credential to equal `intent.agent_pubkey_hex`, and the intent signature, the cart signature, **and** approvals all verified against that one key. Three roles collapsed onto one keypair — so the agent's own key was also the approval key, and the agent could approve its own settlement. The human-in-the-loop gate was cosmetic.

Fixed with real two-key separation. The registered credential is now the **human** key (signs the intent, approvals, revocations); the **agent** key is `agent_pubkey_hex`, embedded in the human-signed intent (so the human attests it) and used only to sign carts and decision narration. `verify.ts` dropped the `AGENT_KEY_MISMATCH` equality rule entirely and now verifies the cart against `intent.agent_pubkey_hex`, not the registered credential. The facilitator's approval/revoke routes already verified against the registered credential, so once registration stored the human key they required the human key with no route change. New adversarial tests encode the fix: the agent key can no longer produce a valid approval or revoke (fail-closed, settlement stays `pending_approval`), and the previously-impossible two-key happy path (intent signed by a distinct human key, cart by the agent key) now verifies. This is the "what broke and how we caught it" story: the RFC described the two-party model correctly all along; the code didn't do it until an adversarial review compared the two.

## 2026-08-23 — Day 1 spike: two assumptions died in contact with reality
1. The S2S JSON create-payment endpoint (the one Razorpay's own MCP server wraps) returned "URL not found" on a fresh test account — it's enablement-gated. Re-architected same hour to the embedded-checkout Playwright driver per the pre-agreed decision rule.
2. Razorpay docs say Orders `receipt` is enforced-unique. It is not — two identical-receipt orders were accepted. Our facilitator's own idempotency store is now the sole dedup guard on order creation. The trust envelope has to bring its own guarantees; the rail provides fewer than documented.
